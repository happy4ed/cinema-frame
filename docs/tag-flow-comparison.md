# 음악 태그 기반 두 경로의 실제 API 비교

2026-11-08. Android 선곡 코드·설치본·재생 상태는 변경하지 않는 호스트 실험이다.

## 조건과 조사 범위

- `비 오는 날 재즈`: 영화의 IMDb 장르를 제한하지 않는다. 곡 태그는 `(재즈 및 하위 장르 OR) AND (calm/chillout/mellow/melancholic/relaxing OR)`.
- `80년대 SF 웅장한`: 영화의 연도 1980–1989, IMDb Sci-Fi. 곡 태그는 `epic OR orchestral OR cinematic`.
- 두 경우 모두 로컬 카탈로그의 평점 7 이상, 투표 10,000 이상, 기존 IN 제외를 적용한다. 평점 내림차순, 투표 내림차순, IMDb ID 순이다.
- OST 먼저: 최대 영화 1,000편. 정확한 영화명과 OST 표기가 일치하는 첫 Deezer 검색 앨범을 확인한다. 앨범당 Last.fm 태그 조회 한 번. 앨범과 곡 모두 장르·분위기 조건을 충족해야 한다. 조건에 맞는 곡 중 Deezer 순위 상위 3곡을 선택하고 ISRC로 Spotify 재생 가능 여부를 검사한다.
- 태그 먼저: 태그당 상위 100곡의 합집합. 한 태그가 조사 예산을 독점하지 않도록 각 목록 내 순위를 번갈아 최대 1,000곡의 실제 곡 태그를 조회한다. 태그 목록 소속과 개별 곡 태그를 합쳐 조건을 확인한 뒤 MusicBrainz recording MBID → ISRC → Deezer 앨범 및 수록곡으로 영화 OST 소속을 검증한다. 같은 Spotify URI는 중복 제거한다. **아래 최초 측정은 개별 곡 태그만 조건에 사용했다. 목록 소속을 함께 인정하는 수정은 캐시에서 오프라인 재집계했으며, 외부 API 검증은 503 이후 재개하지 않았다.**
- 목표는 고유 Spotify 재생 가능 곡 20개. 실험은 곡을 직접 재생하지 않는다. 두 경로 모두 외부 API 오류는 중단하며 임의의 기본값으로 대체하지 않는다.
- BPM은 조회·필터에 사용하지 않는다. 개인 분류 태그는 사전에 없다. API가 반환한 원문에는 개인 태그가 있을 수 있으나 허용 목록과 일치하지 않으면 사용하지 않는다.

## 해석의 한계

- OST 판정은 영화 제목의 정확한 정규화 일치 및 앨범의 OST 표기를 이용한다. 발매 권리자의 공식 인증을 별도로 확인한 것은 아니다. 다른 표기로 발매된 OST를 놓칠 수 있다.
- 태그 먼저 경로에서는 Deezer ISRC 조회가 반환한 발매 앨범을 검사한다. 같은 녹음의 다른 OST 발매본까지 전수 조회한 것은 아니다. 따라서 0곡은 전 세계에 해당 OST가 없다는 뜻이 아니다.
- 태그 먼저 경로는 사용자가 제시한 보조 흐름대로 OST 소속을 검증하며, 영화별 Deezer 상위 3곡 제한은 적용하지 않는다. 두 경로의 검색 표본이 다르므로 효율과 누락 원인을 함께 비교해야 한다.
- Last.fm 호출 간격 목표는 0.25초, MusicBrainz는 1.1초. 실제 기록의 임의 1초 구간 최대 호출은 OST 먼저 4회, 태그 먼저 5회로 사용자 제한을 지켰다. 각 경로의 독립 캐시는 출처·수신 시각·만료 시각을 저장하고 7일 뒤 만료한다. HTTP 요청 수와 캐시 사용 수를 구분한다.
- 곡 태그 없음 비율의 분모는 실제 `track.getTopTags` 조회 수이다. 곡 조회가 0이면 0%가 아니라 측정 불가로 기록한다.

## 실행

```powershell
python -X utf8 tools/compare_tag_flows.py --session-file <로컬 인증 파일 경로>
python -m unittest discover -s tests -p test_tag_flow_comparison.py -v
```

키·세션은 로컬 파일에서만 읽는다. 실제 원문 캐시는 Git에서 제외된 `work/tag-flow-comparison`에 저장한다. 아래에 확정 결과와 공개 가능한 증거를 추가한다.

## 실제 결과 — 미완료

| 요청 / 흐름 | 확인된 OST 곡 / Spotify 재생 가능 | 실제 HTTP 호출 | 시간 | 앨범 태그 없음 | 곡 태그 없음 |
|---|---|---:|---:|---:|---:|
| 비 오는 날 재즈 / OST 먼저 | 조건 통과 0 / 0 | Deezer 1,000 + Last.fm 318 = **1,318** | **343.784초** | **243/318 (76.4%)** | 0회 조회, 측정 불가 |
| 비 오는 날 재즈 / 태그 먼저 | **검증 미완료** | Last.fm 1,021 + MusicBrainz 4 = **1,025** | **268.044초**(중단까지) | 사용하지 않음 | **910/1,000 (91.0%)** |
| 80년대 SF 웅장한 / OST 먼저 | 미실행 | 0 | — | — | — |
| 80년대 SF 웅장한 / 태그 먼저 | 미실행 | 0 | — | — | — |

위 두 실행의 API 캐시 적중은 각각 0회다. 이후 오프라인 재집계는 이미 저장한 응답만 읽었고 추가 HTTP 요청은 없다. 따라서 268초를 완료된 태그 우선 경로의 실행 시간으로 해석하면 안 된다.

OST 먼저는 영화 1,000편 중 정확한 이름 규칙으로 앨범을 찾지 못한 영화 682편, 태그 없는 앨범 243편, 태그가 있지만 조건이 안 맞는 앨범 75편이다. 곡 태그·ISRC·Spotify 단계에는 도달하지 않았다.

태그 먼저는 21개 태그에서 1,937곡의 합집합을 만들고 1,000곡을 조사했다. 최초 측정의 개별 곡 태그만으로는 12곡이 장르·분위기 조건에 맞았다. 태그 목록 소속도 증거로 인정하는 수정 기준으로 캐시를 재집계하면 **13곡**이다. **두 수치 모두 OST 소속·Spotify 재생 가능 곡 수가 아니다.**

MusicBrainz recording 조회 세 건이 404를 반환했고 네 번째가 **HTTP 503**을 반환했다. Last.fm MBID가 해당 recording 조회에서 해석되지 않았다는 사실만 확인했으며, 404의 원인을 단정하지 않는다. 503의 서버 내부 원인이나 요청 제한 여부도 확인하지 못했다. 지시대로 API 호출을 중단하고 SF 실험도 진행하지 않았다. 실패 응답을 0곡이나 성공으로 치환하지 않았다.

## 다음 선택지

1. 서비스 회복 후 캐시를 유지하고 중단한 조회를 재개한다. 404 MBID에는 곡을 대체하지 않고 미확인 사유를 남긴다.
2. 보조 흐름의 녹음 식별 경로를 별도 검토한다. Last.fm MBID가 recording 조회에서 해석되지 않는 경우가 있어, 이 의존성을 해결하지 않으면 비교 결과가 태그 검색보다 ID 연결 실패에 좌우될 수 있다.

현재 숫자로 기본 흐름을 결정할 근거는 부족하다. 다만 **앨범 태그를 필수 관문으로 두는 방식의 낮은 통과율**은 이번 표본에서 확인됐다. 이를 완화하거나 기본 흐름을 바꾸는 앱 구현은 아직 하지 않았다.
